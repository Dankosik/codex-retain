# Оптимизация производительности — 10 сентября 2026

Реализованы шесть основных направлений из [аудита](performance-audit-2026-09-10.md): инвентарь кандидатов, ограниченный фоновый отчёт, сохранение групп при конфликтах, переиспользование проверки владельцев, выборочный разбор JSON и устранение повторной работы с metadata/выводом.

В итоговой серии очистка свободных соседей одного занятого файла ускорилась в 30,5 раза; наблюдаемый RSS смешанного профиля уменьшился в 7,4 раза, фонового прохода по 100 000 архивов — в 9,2 раза. Обычная очистка 10 000 архивов заняла на 7,6% меньше времени. На 1 000 архивов elapsed практически не изменился.

Исходное состояние включает незакоммиченные изменения, существовавшие перед реализацией, в том числе типизированные причины результата и переиспользование prepared statements. Базовый release-бинарник собран из отдельного снимка этого дерева. Его SHA-256 — `2329dc3a45932dcd1f5abae82ebe9903f8aa9f240cede008c05fa94f713ef34c`; итоговый кандидат — `d3f148fad71187919d3a435bc8625581d620c97b914b4c59c2dc99002ff4e4d3`.

## Что изменено

Начальный SQL-read передаёт строки обработчику по одной. Непросроченные строки не остаются большим `Vec<Thread>`. Для кандидатов сохраняются только индекс результата и путь; ID, заголовок, срок и статус хранятся один раз. Весь ограниченный read завершается до удаления, включая проверку 100 001-й строки.

Инвентарь продолжает обходить обе директории и проверять каждый entry, но хранит лишь кандидатов: «не найден / единственный путь / неоднозначно». Количество directory entries по-прежнему ограничено 500 000; проверка посторонних symlinks не пропускается. Проверка канонического UUID использует стековый буфер вместо временной строки.

Scheduled-режим сохраняет только необходимое состояние кандидатов, десять диагностических строк и десять предупреждений. Индексы диагностик сохраняют исходный порядок, включая ошибки, найденные позже при удалении. После обработки освобождается и ёмкость большого рабочего вектора; возвращаемый отчёт содержит не более десяти примеров. Обычный полный JSON сохраняет прежнюю схему и детализацию.

Кеш владельцев привязан к одному `Connection`. В каждой immediate-транзакции проверяются `data_version` и `total_changes`; внешние commits требуют новой проверки, неизвестные локальные записи запрещают дальнейшее переиспользование. Признанным локальным изменением может быть только успешно закоммиченное проверенное удаление. Кеш хранит общий префикс один раз и одну пару «имя / ID» на plain+zstd представления. SQLite фильтрует строки по включительным лексическим границам до передачи в Rust. Для допустимых логических написаний с `/./` или повторными разделителями сохраняется отдельный точный ключ после проверки соответствия физическому файлу.

Занятый UUID выделяется из группы, свободные соседи остаются сгруппированными. Неидентифицированная локальная ошибка проверки вызывает ограниченное итеративное разделение группы. Общая недоступность maintenance/coordinator/schema и SQLite busy останавливает дальнейшие группы. Любая попытка записи journal или pending intent по-прежнему запрещает повтор удаления.

Парсер первой строки хранит результаты четырёх проверок вместо полного JSON-дерева. При этом весь JSON, включая неиспользуемые значения, проверяется; сохранены duplicate-key semantics, UTF-8, ограничения чисел и вложенности, порядок ошибок. File metadata возвращается вместе с проверенным handle и используется повторно без соседнего `fstat`. Stdout получает отдельный буфер 64 КиБ, явный flush и обработку BrokenPipe в том числе через Serde.

Схема SQLite, набор зависимостей, версия адаптера, размер группы 128, durable journal и порядок fsync/commit не изменены. Локальные тесты и измерения использовали только синтетические профили.

## Метод измерения

Rust 1.98.1, release с Thin LTO, macOS ARM64. Hyperfine: три прогрева и пять измерений на случай; сохраняются все значения и разброс. Baseline/candidate одной пары используют один путь и одну исходную фикстуру. Перед каждым разрушительным образцом восстанавливаются seed SQLite и только ранее удалённые синтетические rollouts; удерживаемые чужие lock inodes сохраняются. Подготовка, проверки policy/identity и постусловия находятся вне timed command.

Проверяются точные ID и пути, содержимое оставшихся файлов, значения epochs, остальные колонки surviving rows, схема и другие таблицы, policy и защищённые индексы, отсутствие pending intent, foreign keys и целостность SQLite. RSS наблюдается отдельно через `ps` у процесса Retain: это нижняя оценка пика, исключающая дочерний Codex, а не allocation profile или одновременная память дерева процессов.

## Проверки и доказательства

Прошли 127 Rust-тестов, 20 тестов измерительного скрипта, `cargo fmt --all -- --check`, `cargo clippy --locked --all-targets -- -D warnings`, locked release build и `git diff --check`. Это включает двухсоединительные WAL-проверки invalidation/rollback, границы batch/recovery, неизменность чужих lock inodes, первые десять late-discovered diagnostics, raw logical spellings, строгую проверку лимита до удаления и реальный BrokenPipe/exit-status путь CLI.

Итоговая матрица содержит 20 комбинаций сценарий/бинарник, 100 измеренных native запусков и по три прогрева на комбинацию. Профиль был синтетическим; model turns и LaunchAgents не создавались.

## Промежуточные эксперименты

Первый кандидат (`5580dec11a49b44f45e35775f5868a459cec6a68869fb3942eb8ef9d5471cf3a`) сохранял дополнительные полные пути и дублировал рабочие записи. В первой серии обычная очистка оказалась медленнее: 556 против 456 мс на 1 000 и 12,05 против 7,94 с на 10 000. Последующее отдельное профилирование дало обратное соотношение elapsed (6,29 против 9,69 с), поэтому причинный вывод о всей временной разнице не установлен. Однако повышенное удержание памяти подтверждалось: sampled physical-footprint peak 26,5 против 16,5 МиБ.

Эта версия переработана: убраны дубликаты записей, общий префикс и plain/zstd ключи сжаты, лишние строки остаются отфильтрованными внутри SQLite. Неудачные серии и профили сохраняются отдельно от окончательного сравнения.

Первый запуск большой матрицы был остановлен во время повторной проверки файлов, до получения candidate timing. Измерительный скрипт затем перестал повторно проверять каждый родительский компонент каждого пути и несколько раз хешировать всю фикстуру. Полные preflight/postflight проверки сохранены, для разрушительных случаев остаются проверки после каждого образца. Это изменение измерительного скрипта не считается ускорением Retain.

## Воспроизведение

Сначала собрать и сохранить оба release-бинарника. Затем выполнить с явными путями:

```sh
/opt/homebrew/bin/rtk proxy python3 scripts/performance_matrix.py run \
  --baseline /absolute/path/to/baseline \
  --candidate /absolute/path/to/candidate \
  --codex-bin /absolute/path/to/compatible-codex \
  --root /private/tmp/new-retain-performance-run \
  --cases cleanup mixed summary contention headers --all-busy --rss
```

Каталог должен отсутствовать и находиться вне репозитория. Случай `headers` требует `zstd`. Команда не собирает проект и не устанавливает расписание. Нельзя запускать конкурирующие сборки или бенчмарки во время измерений.
