# Производительность 0.1.1 и 0.1.2 — 10 сентября 2026

В проверенной нагрузке из 1 000 независимых paginated-архивов медиана выросла
на 8,4%: с 729 до 790 мс. Это ближе к текущему формату пользовательской истории,
но не воспроизводит её дерево связей и размеры файлов. Массовая очистка legacy
и большой общий инвентарь регрессировали значительно сильнее. Оптимизация
инвентаризации обоснована; обычный фоновый проход остаётся небольшим по
абсолютному времени.

## Сопоставимые измерения

Сравнивались установленные release-бинарники 0.1.1 и 0.1.2, без пересборки.
Оба выпущены для ARM64 с Rust 1.98.1; измерения сделаны на одном macOS 26.4
хосте. Кодек Codex — embedded 0.153.4. Профили исключительно синтетические,
файлы независимых архивов — 4 КиБ. Обе версии каждой пары используют один
путь, политику и исходный набор файлов. Для paginated изменены заголовки и
SQL history_mode; тела остаются синтетическими и не проверяют native rendering.

Hyperfine: три прогрева, затем пять измерений. Подготовка, восстановление
исходной фикстуры и проверки результатов находятся вне timed command.
Разрушительные примеры восстанавливаются перед каждым запуском. Порядок версий
чередуется между сценариями. Измерения и профилирование выполнялись последовательно,
без параллельной сборки. Все образцы сохранены, включая выбросы.

| Нагрузка | 0.1.1, медиана | 0.1.2, медиана | Изменение |
| --- | ---: | ---: | ---: |
| Очистка 1 000 независимых paginated-архивов | 0.729 с | 0.790 с | +8.4% |
| Очистка 1 000 legacy-архивов | 0.446 с | 0.564 с | +26.5% |
| Очистка 10 000 legacy-архивов | 9.250 с | 34.528 с | +273.3% |
| Scheduled: 100 000 архивов, ни одного просроченного | 0.368 с | 0.557 с | +51.4% |
| Preview: 99 000 активных + 1 000 непросроченных | 0.153 с | 0.314 с | +104.9% |
| Preview: тот же профиль, один просроченный архив | 0.233 с | 18.115 с | +7661.6% |

Это warm-cache серия на работающем desktop-хосте, без изоляции CPU и сброса
дискового кеша. Для 10 000 legacy-архивов среднее было 9,518 ± 2,128 с против
42,401 ± 24,441 с; диапазоны — 7,773–13,119 и 19,085–79,777 с. Медиана показывает
рост в 3,73 раза, среднее — в 4,45 раза. Все пять новых проходов дольше всех
пяти старых, но коэффициент нельзя переносить на любой компьютер и профиль.

В scheduled-сценарии диапазоны пересекаются: 343–471 мс и 350–1 665 мс.
Надёжно приписать всё наблюдаемое изменение этого короткого пути коду нельзя.
Для смешанного профиля с одним просроченным архивом диапазоны разнесены:
233–247 мс против 16,677–22,329 с. Там появился существенный дополнительный I/O.

## Причина и профиль

В 0.1.1 legacy-кандидаты не запускали сканирование всех заголовков lineage.
Paginated уже требовали его. В 0.1.2 родительские ссылки из заголовков и копии
файлов учитываются для обоих форматов, поэтому полное чтение выполняется при
наличии любого кандидата. Свежий скан также повторяется внутри транзакции
перед каждой группой удаления: [delete_batch](../src/engine.rs),
[scan](../src/lineage.rs).

Для 10 000 независимых просроченных файлов без внешних изменений получается
79 групп по максимум 128 файлов. Начальный скан и повторные сканы оставшихся
файлов дают 405 632 посещения заголовков, не считая отдельных проверок самих
кандидатов. Это расчёт по алгоритму, не измеренный счётчик системных вызовов.
При большом количестве активных файлов они остаются в каждом таком обходе.

Отдельный трёхсекундный sample read-only preview смешанного профиля собрал
2 388 наблюдений главного потока: в 1 801 сверху был read, в 393 — open.
То есть около 91,9% наблюдений приходились на открытие и чтение файлов через
lineage::scan. Это доли sampled stacks, не точные проценты wall time и не
измерение физических disk-read bytes. JSON-разбор был значительно меньшей
частью именно этого профиля. Профилированный запуск занял 13,652 с и не входит
в Hyperfine-серию.

[Raw sample](evidence/performance-0.1.2/profile-mixed-one.txt),
[проверка результата профилирования](evidence/performance-0.1.2/profile-receipt.json).

## Что имеет смысл оптимизировать

1. Основной приоритет — переиспользование проверенной информации о заголовках
   с надёжным обнаружением новых, заменённых и изменившихся файлов. Свежесть
   инвентаря и зависимостей перед удалением должна сохраниться. Один только
   SQLite data_version не подтверждает неизменность orphan-файлов; простое
   повторное использование старого графа не является безопасным решением.
2. Малое отдельное улучшение — объединить source и staging directories в один
   набор перед fsync. Для обычного плоского архива это сейчас одна и та же папка,
   которую delete_batch синхронизирует дважды подряд до удаления SQL-строк.
   Устранение дубликата не требует убирать durability barrier. Величина выигрыша
   ещё не измерена и не объясняет всю наблюдаемую регрессию.

Для текущего объёма paginated-истории срочная широкая переработка не требуется.
Для масштабирования на десятки тысяч файлов узкая оптимизация инвентаря имеет
смысл. Из этой серии нельзя обещать конкретное ускорение будущего кандидата.

## Проверки и границы

Получены 60 измеренных запусков в 12 комбинациях сценарий/версия, с тремя
прогревами каждой. Все 24 preflight/postflight receipts подтверждают ожидаемые
counts, оставшиеся строки, неизменность защищённых метаданных и эпох,
отсутствие pending recovery. Каждый measured destructive run также проходил
проверку через conclude callback. [Компактная проверка](evidence/performance-0.1.2/validation.json)
содержит SHA-256 полных сжатых receipts.

Не измерялись cold-cache, 10 000 paginated-архивов, реальные пользовательские
4 ГБ файлов, граф связанной семьи, задержки живого Codex writer и другие
платформы. Прежняя версия пропускает spawn-related чаты, поэтому такое время
нельзя выдавать за сопоставимую скорость их полноценного удаления.

Production-код, установленная версия, политика и расписание не изменялись.
Оптимизация пока не реализована и не опубликована.

## Воспроизведение

Бинарники обеих версий должны существовать до запуска. Новые root должны
отсутствовать; harness отказывается переиспользовать произвольные профили.

```sh
/opt/homebrew/bin/rtk proxy python3 scripts/performance_matrix.py run \
  --baseline /opt/homebrew/Cellar/codex-retain/0.1.1/bin/codex-retain \
  --candidate /opt/homebrew/Cellar/codex-retain/0.1.2/bin/codex-retain \
  --codex-bin /Applications/ChatGPT.app/Contents/Resources/codex \
  --root /private/tmp/new-retain-legacy-comparison \
  --cases cleanup summary mixed --runs 5

/opt/homebrew/bin/rtk proxy python3 docs/evidence/performance-0.1.2/paginated_matrix.py run \
  --baseline /opt/homebrew/Cellar/codex-retain/0.1.1/bin/codex-retain \
  --candidate /opt/homebrew/Cellar/codex-retain/0.1.2/bin/codex-retain \
  --codex-bin /Applications/ChatGPT.app/Contents/Resources/codex \
  --root /private/tmp/new-retain-paginated-comparison \
  --cases cleanup --runs 5
```

Paginated adapter намеренно выбирает только cleanup-1000 и использует
существующие механизмы marker, подготовки, восстановления и проверок matrix.
