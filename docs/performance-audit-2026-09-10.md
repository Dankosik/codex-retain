# Аудит производительности Codex Retain — 10 сентября 2026

Самые перспективные изменения: сохранять групповую очистку при единичных конфликтах, ограничить инвентаризацию кандидатами, сократить состояние фонового отчёта и убрать повторное сканирование `threads` между группами. Мелкие аллокации и параметры компилятора имеют меньший приоритет: свежий профиль обычной очистки показывает большую долю ожидания файловых операций.

Это анализ зафиксированного исходного состояния с последующей сверкой параллельных изменений. В рамках аудита я не менял исполняемый код, зависимости, реальные профили или LaunchAgent. Уже существовавшие незакоммиченные оптимизации включены в исходное состояние. Возможные ускорения ниже не выдаются за внедрённые или измеренные результаты.

**1. Сохранять группы при локальном конфликте — высокий приоритет для очистки**

[apply_group](../src/engine.rs#L603) при ошибке до journal сразу повторяет всю группу по одному элементу. Один постоянно занятый UUID среди 128 превращает 127 успешных удалений в 127 отдельных циклов journal/commit/fsync. Это возвращает дорогую поштучную обработку, от которой проект уже уходил.

Направление: разделять конфликтную группу пополам либо возвращать из acquisition точную локальную причину и формировать группы из свободных участников. При бинарном разбиении вокруг одного конфликта 127 свободных элементов укладываются в семь успешных групп: 64 + 32 + 16 + 8 + 4 + 2 + 1. Это расчёт количества групп, не обещание ускорения в 18 раз.

Дополнительно различать локальный writer conflict и общую недоступность maintenance/coordinator/schema: повторять общий отказ для каждого архива бессмысленно. Сохранить допустимый код завершения и диагностирование пропусков. Разбиение разрешено только до начала journal, при отсутствии pending и без SQLite busy; после возможного эффекта остаётся нынешняя остановка/recovery.

Проверить 0, 1/128, 10% и 100% занятых участников; конфликт в начале/середине/конце; число успешных durability-групп, elapsed и задержку других writers. При множестве конфликтов бинарное дерево может увеличить число неудачных попыток, поэтому нужен ограниченный алгоритм.

**2. Хранить инвентарь только для кандидатов — высокий приоритет для памяти**

[Inventory::scan](../src/engine.rs#L213) строит `HashMap<String, Vec<PathBuf>>` для всех распознанных rollout-файлов в `sessions` и `archived_sessions`. Он запускается при наличии хотя бы одного просроченного кандидата. Разница 7,1 → 52,2 МиБ в новом смешанном сценарии согласуется с этим путём; это наблюдение текущего кода, а не измерение исправления.

Сначала собрать множество идентификаторов просроченных кандидатов, затем пройти весь инвентарь, сохраняя только совпадения. Вместо списка всех дубликатов достаточно состояния «единственный путь / неоднозначно». Для недвусмысленного кандидата сохранить путь, необходимый проверкам и обнаружению republish.

При `F` найденных файлах и `D` кандидатах удерживаемое состояние меняется с порядка `O(F × длина пути)` на `O(D × длина пути)`. Время обхода остаётся `O(F)`: всё равно нужны проверки symlink, ошибок обхода, лимита 500 000 entries и дубликатов в активной директории. Обход только `archived_sessions` не сохраняет текущий контракт.

Следующая проверка: независимое изменение `F` и `D`, длинные пути, plain/zstd-двойники, почти предельный инвентарь. После этого можно отдельно измерить компактный UUID-ключ вместо выделяемой `String`; сначала лучше устранить ненужные записи целиком.

**3. Сократить состояние scheduled-отчёта и начальной выборки — высокий приоритет для памяти**

[engine::execute](../src/engine.rs#L694) получает `Vec<Thread>`, затем формирует полный `Vec<Entry>` и очередь индексов `due`. [Scheduled caller](../src/lib.rs#L312) ничего не печатает и сохраняет лишь счётчики и десять диагностических примеров, но всё равно создаёт полный отчёт. На 100 000 непросроченных строк наблюдалось около 66 МиБ RSS даже при нуле удалений.

Разделить внутреннюю обработку и объём сохраняемой детализации: полный результат для существующего JSON, агрегаты и ограниченные примеры для scheduled, при необходимости первые 30 записей для текстового вывода. Нужны отдельный общий флаг attention, компактные IDs кандидатов и данные для republish-проверки: простое усечение `entries` сломает обработку и exit status.

Это не делает весь процесс `O(1)`: начальный `Vec<Thread>` и кандидаты останутся. Второй шаг — читать metadata потоково или ограниченными страницами, не создавая большой промежуточный вектор. При этом лимит 100 000 архивов должен проверяться до первого удаления; нельзя удалить префикс и лишь потом обнаружить 100 001-ю строку. Сохранить порядок, семантику конкурирующих изменений и полный JSON-контракт. Для полного JSON допустимо исследовать временный spool, но его I/O имеет собственную цену.

**4. Убрать повторный полный обход owners — высокий приоритет для масштабирования**

[verify_rollout_owners](../src/engine.rs#L568) выполняет `WHERE rollout_path IN (…)` внутри каждой группы. Индекса `rollout_path` нет. При `N` строках и `D` удалениях число посещений строк порядка `O(ND/B)`, где `B=128`; если удалить всю таблицу — примерно `N²/(2B)`. Получается около 396 тысяч посещений при 10 тысячах архивов и 39,1 миллиона при 100 тысячах. Большой постоянный набор активных строк делает каждый проход дороже.

Два возможных решения требуют сравнения:

- Управляемый индекс по `rollout_path`: сохраняет свежую SQL-проверку внутри транзакции и заменяет обходы индексными поисками. Потребуется изменение capture/schema lifecycle, проверка старых readers, места на диске, WAL и дополнительной стоимости native insert/update/delete. Просто добавить индекс в чужую SQLite нельзя: текущий адаптер отвергнет неизвестную схему. [Механика индексного поиска SQLite](https://www.sqlite.org/queryplanner.html).
- Кеш owners на время одного запуска с доказанной инвалидацией внешних изменений. Перестраивать под `BEGIN IMMEDIATE`, хранить только релевантные кандидатам пути, учитывать собственные удаления. `PRAGMA data_version` различает внешние commits только при сравнении на одном соединении; собственные commits его не меняют. Это основание для эксперимента, не готовое доказательство безопасного кеша. При постоянных внешних writes худшая сложность может остаться прежней. [Контракт data_version](https://sqlite.org/pragma.html#pragma_data_version).

При обоих подходах сохраняются текущие row/epoch/pin/path/identity проверки, aliases logical/plain/zstd и смена владельца между группами. Однократный неинвалидируемый owner-map недостаточен. На текущих 10 000 файлах это может сэкономить CPU без большого elapsed-выигрыша: свежий профиль прежде всего указывает на файловые операции.

**5. Разбирать нужные поля заголовка без полного JSON-дерева — средний приоритет, особенно для больших headers**

[inspect](../src/engine.rs#L317) читает ограниченную первую строку, но строит полный `serde_json::Value`. Проверкам нужны только `type`, `payload.id`, `history_mode` и `history_base`. Большой неиспользуемый объект или множество маленьких значений создают лишние аллокации. В успешном cleanup разбор выполняется дважды: предварительно и под блокировками.

Можно десериализовать только нужные поля, пропуская остальные значения с полной проверкой синтаксиса. Сначала сохранить нынешний ограниченный line-buffer: это проще для совместимости. При подходящем вводе Serde допускает заимствование строк из входного буфера; экранированные значения могут требовать выделения памяти. [Документация Serde](https://serde.rs/lifetimes.html).

Обычная derived-структура не полностью эквивалентна `Value`: нужно сохранить поведение повторяющихся ключей, отсутствующих/null полей, escapes и trailing syntax. Остаются newline, лимит первой строки 1 МиБ и окно zstd 8 МиБ. Ограничение окна не означает ограничение всей памяти decoder/process восемью МиБ. Кешировать предварительное разрешение на удаление вместо повторной проверки под lock нельзя.

Измерять отдельно маленький типичный header, большой игнорируемый string и объект с множеством полей, каждый в plain и zstd. Нынешние throughput-замеры с небольшим header эту возможность не проверяют.

**6. Удалить дублирующие syscall и аллокации — меньший, понятный объём работ**

- [regular](../src/fsutil.rs#L42) уже получает `Metadata`, а `inspect`, finalization, recovery и database identity сразу запрашивают её ещё раз. Возвращать проверенную metadata вместе с File там, где она сразу нужна: около трёх соседних лишних `fstat` на успешно удаляемый файл. Сохранить `NOFOLLOW`, `NONBLOCK`, nlink и все проверки на границах фаз. В текущем профиле `fstat` малозаметен, поэтому большого elapsed-выигрыша не ожидаю без дополнительных данных.
- Перемещать `id/title` из потребляемого `Thread` после inspection, вместо `clone`; избежать повторного форматирования одной ошибки для каждого участника группы; резервировать обоснованный размер результата. Это работа над allocation churn, не доказанное ускорение команды.
- Для большого JSON stdout сравнить нынешний `StdoutLock` с явным ограниченным `BufWriter`, сохранив flush и BrokenPipe. State/journal JSON уже буферизован. [Контракт BufWriter](https://doc.rust-lang.org/std/io/struct.BufWriter.html).
- Повторное использование read/decoder buffers проверять после изменения парсинга. `clear()` сохраняет максимальную capacity: один крупный header не должен бесконтрольно увеличивать длительно удерживаемый буфер.

**7. Другие поверхности: что имеет смысл исследовать позже**

Начальный [запрос архивов](../src/database.rs#L265) зависит от всей `threads`, а лимит ограничивает только возвращённые архивы. На смешанных профилях стоит сравнить планы с использованием имеющегося archive-индекса. Замена условия на `archived=1` теряет диагностику неизвестных archive states; существующий порядок по ID также нужно сохранить.

[Scheduler runner](../src/scheduler.rs#L192) проверяет завершение процесса с шагом 20 мс; `verify_binary` — с шагом 5 мс. Для коротких status/doctor/enable это добавляет задержку обнаружения выхода. Можно измерить ожидание с deadline без периодического polling; для получения UID уже имеющийся rustix с нужной feature потенциально заменяет `/usr/bin/id`. Это не горячий цикл очистки, а операции с фиксированным объёмом работы. Отказ от проверки версии Codex или кеширование её без надёжной инвалидации не подходит.

Большие группы 256/512 могут уменьшить количество durability-циклов, но увеличат число FD, время удержания UUID/SQLite lock, размер journal и требования recovery-совместимости. Проверять их только вместе с p95/p99 задержки native writers и конфликтными сценариями. Сначала выгоднее сохранить нынешние группы при локальных конфликтах.

LTO/codegen-units, PGO, allocator, другой hasher, SIMD, mmap и параллельная обработка остаются экспериментами после устранения повторной работы. В release уже есть Thin LTO; профиль не обосновывает новый runtime или unsafe. Параллельный decode может умножить decoder/buffer memory, а параллельное удаление конкурирует за SQLite и файловые barriers. Без замеров это обмен сложности на неизвестный результат.

**Что уже сделано и не требует повторной оптимизации**

В дереве уже присутствуют batch 128, буферизованная запись journal, освобождение глобальной coordination на время I/O, переиспользование prepared SELECT/DELETE, `Decoder::with_buffer` и один `String` в `safe_text`. [Предыдущий эксперимент](performance-experiments-2026-09-10.md) показал снижение user CPU на 26–39% от statement reuse, но не показал ускорения полной очистки. Immutable reference caching проверяли и убрали из-за отсутствия убедительного выигрыша.

Планы synthetic SQLite не выявили неиндексированных child FK при DELETE: `thread_dynamic_tools` и `thread_artifacts` имеют подходящие индексы; spawn-edge lookup использует оба имеющихся индекса; capture удаляет epoch по PK. В `threads` 20 индексов вместе с PK, восемь частичных: их поддержка является частью работы совместимого удаления. [Планы и схема](evidence/performance-audit-2026-09-10/sqlite_plan_audit.json). Это Python SQLite 3.51.3, пустая схема без ANALYZE; планы bundled SQLite рабочего бинарника и statement counters ещё не измерены.

**Практическая очередность**

1. Инвентарь только для кандидатов и bounded scheduled report: уже есть отличающие входы и наблюдения роста памяти.
2. Локализация batch-конфликтов: сравнить количество journal/commit циклов и полное время.
3. Owners lookup: отдельно сравнить управляемый индекс и корректно инвалидируемое состояние на смешанных и 100k-профилях.
4. Селективный JSON parsing и соседние повторные metadata-вызовы.
5. Начальная выборка, stdout, startup, параметры компилятора — по оставшемуся профилю.

Для каждого изменения сравнивать точные release-кандидаты на одинаковых fixtures: elapsed и разброс, user/system CPU, RSS/allocations, задержку конкурирующей записи, outputs и постусловия восстановления. Тёплый кеш, холодный кеш, большие headers и contention — разные нагрузки. Скорость после отключения `fsync`, `synchronous=FULL`, защиты pins/aliases или свежих проверок не соответствует нынешнему продукту.

**Воспроизведение новых наблюдений**

Нужны release-бинарник указанной идентичности, совместимый native Codex, Hyperfine и новый каталог вне репозитория. Сначала подготовить marker-checked root штатным `scripts/benchmark.py run --retain-only --counts 10000 --only cleanup --runs 5 --prepare-only`, передав явные `--root`, `--retain`, `--codex-bin`. Затем запустить `python3 docs/evidence/performance-audit-2026-09-10/mixed_probe.py /absolute/marked/root`.
